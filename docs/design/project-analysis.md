# 天枢（Tianshu）项目分析

> 天枢 Tianshu — Async AI Orchestration Core

---

## 一、项目概览

### 命名由来

"天枢"取意于北斗七星之首。北斗七星传统星名依次为天枢、天璇、天玑、天权、玉衡、开阳、瑶光，其中天枢居首，天然具备"核心、中枢、统领、起始"的象征意义。

### 项目定位

天枢是一个面向复杂任务处理的**异步 AI 多智能体执行平台**。运行在容器环境中，集成 Skills、Agents、文件检索、工具调用与任务调度能力，支持用户以"下发任务"的方式完成工作委托，由系统自动拆解任务、组织智能体协作执行，并输出结构化结果、过程记录与决策建议。

一句话概括：

> **白天下旨，夜间办差，早上递折子。**

### 核心理念

1. **AI 不是聊天框，而是可调度的执行体系**——天枢是能够理解任务、分配职责、调用能力、跟踪过程、汇总结果的智能执行中枢。
2. **复杂任务不必实时完成，更适合异步完成**——系统不限于夜间场景，"异步批量执行"是核心模式，夜间只是其中一种调度策略。
3. **真正有价值的不是单 Agent，而是有秩序的协同组织**——借鉴中国古代朝廷行政制度，通过统一调度、职责分层、结果审计和经验沉淀，构建可管理、可追踪、可复盘的执行体系。

## 二、技术可行性

天枢所需的能力链条：

```
任务下发 → 任务排队 → 定时调度 → Agent 分解 → Skills/Tools 执行 → 结果汇总 → 结果汇报
```

各层均有成熟基础设施支撑：

| 层次 | 技术方案 | 说明 |
|------|----------|------|
| 容器执行层 | Kubernetes CronJob | 按周期启动一次性 Job |
| 长流程与失败恢复层 | Temporal Workflows/Schedules | Durable Execution，流程中断可从事件历史恢复 |
| Agent 能力层 | Agents SDK + Skills + Tool Search | 多 Agent、工具调用、handoff、trace；Skills 封装可复用能力包；Tool Search 动态发现工具 |
| 知识与检索层 | File Search + Web Search | 文件知识库检索 + 外部信息补充 |
| 异步执行层 | Background mode + Batch API + Webhooks | 长任务后台执行、50% 价格折扣的批量处理、完成通知回调 |

**结论**："容器化 AI 执行班底"不是概念问题，而是一个工程编排问题。

---

## 三、场景匹配度

以下任务天然适合异步执行：

| 场景 | 特点 |
|------|------|
| 大规模代码扫描 / 批量修复建议 | 耗时长、可批处理 |
| 文档整理、周报、复盘、知识抽取 | 步骤多、流程明确 |
| 多来源情报归集 | 可并行、可排队 |
| RAG 建库、向量化、索引更新 | 对实时性不敏感 |
| 多轮代理评审、对比实验、评分 | 需要多角色协作 |
| 次日汇报材料预制 | 天然适合"下发-执行-回报"模式 |

共同特点：**耗时长、步骤多、可排队、可批处理、对秒级反馈不敏感**。

## 四、竞品对比与差异化

| 已有方案 | 能力范围 | 天枢的差异化 |
|----------|----------|-------------|
| ChatGPT + Background mode | 单任务异步执行 | 天枢支持**批量任务编排**与**多 Agent 协作** |
| n8n / Dify 等工作流平台 | 可视化拖拽流程 | 天枢更偏向 **AI-native 的任务理解与自动拆解** |
| 普通 CronJob 脚本 | 定时运行固定脚本 | 天枢的任务是**自然语言下发、动态拆解** |
| Claude Code / Cursor Agent | 交互式 AI 编程 | 天枢是**离线异步执行，无需人在线** |
| AutoGPT / CrewAI | 多 Agent 框架 | 天枢强调**治理制度**而非无序协作 |

**核心差异化**：自然语言任务输入 → 自动拆解 → 异步可靠执行 → 结构化结果回报。

## 五、价值分析

### 5.1 直接价值：效率与成本

当前 AI 辅助工作的痛点：白天需要人盯着执行、API 排队体验差、任务被交互打断、做完没有沉淀复盘。

天枢将模式改为"**下发 → 执行 → 回报**"，可量化的节省：

```
节省价值 = (陪跑时间 × 人力成本) + (Batch API 50% 折扣 × 调用量) + (错峰执行的稳定性收益)
```

一个团队如果每天有 3-5 个"需要跑 30 分钟以上"的 AI 任务，一年节省的人力陪伴时间约 **300-500 小时**。

### 5.2 管理价值：治理制度解决多 Agent 系统的核心难题

单 Agent 的问题——上下文超限、职责不清、任务冲突难追责、权限边界模糊、难以复盘——天枢通过"朝廷制度映射"系统性解决：

- 不直接操纵每个工具，而是给"内阁"定目标
- 各"部"各司其职，职责边界清晰
- 都察院独立审计，不让执行者自证清白
- 诏令、奏折、批红形成结构化记录
- 每个角色只拿自己该拿的权限

### 5.3 产品价值：趣味性是被低估的竞争力

- **记忆成本低**："内阁拆任务、兵部去执行、都察院来审计"——听一遍就懂，过一个月还记得
- **沟通成本低**：汇报时说"借鉴明朝内阁制的 AI 调度系统"比"multi-agent orchestration framework"有画面感得多，**能讲故事的项目活得更久**
- **设计约束是好事**：当纠结"要不要加一个新 Agent"时，问自己"它对应朝廷里的什么角色？"——答不上来说明可能不需要，避免过度设计

### 5.4 长期价值：从工具到平台

持续演进方向：

- 个人 AI 指挥台 → 团队 AI 调度平台 → 多智能体工作中台 → 治理与沉淀平台

## 六、架构设计：朝廷制度映射

### 6.1 为什么这套隐喻成立

明朝行政制度和多 Agent 系统面临的是**同一类问题**：

| 朝廷面临的问题 | 多 Agent 系统面临的问题 | 解法同构 |
|---|---|---|
| 皇帝精力有限，不可能事必躬亲 | 用户不可能实时监控每个 Agent | 委托与分层 |
| 六部互相推诿、职责交叉 | Agent 之间任务边界模糊、重复执行 | 职责明确划分 |
| 奏折泛滥，皇帝信息过载 | 结果输出杂乱，用户无法快速决策 | 结构化汇报与过滤 |
| 贪腐、欺上瞒下 | Agent 幻觉、越权调用、结果造假 | 独立审计机制 |
| 远程治理、信息延迟 | 异步执行、无法实时干预 | 规则先行、事后追责 |

不是"套皮"，而是用一个**经过几百年验证的治理架构**来解决真实的系统设计问题。

### 6.2 四大核心机制

#### 诏令制：所有任务必须结构化下发

每个任务变成"诏令"格式：任务目标、截止时间、优先级、可调用资源、禁止事项、输出格式、汇报对象、是否需要复核。系统从第一天就天然适合审计和自动化。

#### 内阁制：负责拆解，而不是直接执行

"内阁"不干活，而是把目标翻译成可执行计划——任务拆解、指派各部、协调冲突、汇总奏报。对应 Planner Agent / Orchestrator Agent。

#### 六部制：按职责分治

| 部门 | 职责映射 |
|------|----------|
| 吏部 | Agent/Skills 注册、权限、身份、配额 |
| 户部 | token 成本、预算、API 配额、资源账本 |
| 礼部 | Prompt 模板、输出规范、汇报格式 |
| 兵部 | 执行代理、自动化脚本、容器调度、批处理 |
| 刑部 | 失败处理、回滚、异常升级、风险封禁 |
| 工部 | 工具链、环境、镜像、索引、知识库建设 |

#### 都察院制：独立审计

不负责完成任务，只负责检查：是否越权调用工具、是否偏离原始目标、是否输出虚构结果、是否遗漏失败重试、成本是否超标、结果是否需要人工复核。**这层做好，项目从"炫酷"变成"可上线"。**

### 6.3 推荐的核心角色（v1 控制在 4-7 个）

| 角色 | 古名 | 职责 |
|------|------|------|
| 主理人接口 | 御案台 | 用户下发任务的入口 |
| 总调度 | 内阁首辅 | 理解目标、拆任务、排优先级、选择 Skills/Agents |
| 执行器 | 兵部执行司 | 调用容器、脚本、API、检索、代码代理去执行 |
| 知识库 | 文渊阁 | 记忆、知识库、历史任务、经验沉淀 |
| 审计 | 都察院 | 审计、抽查、风控、失败归因 |
| 通知 | 通政司 | 晨报、告警、日报、任务状态通知 |
| 成本管控 | 户部 | token 预算、API 配额、资源追踪 |

### 6.4 命名原则

外层古风，内层现代：

- 外层：诏令、奏折、内阁、都察
- 内层：scheduler、planner、executor、audit、memory、tool_registry

## 七、风险评估与应对

### 风险 1：多 Agent 协作可靠性不足

当前 LLM 的可靠性还不足以支撑无人监督下的多步长链任务。Agent 之间的"协商"本质上是 prompt 路由，效果不稳定。

**应对**：v1 先做单 Agent + 工具调用的可靠执行，多 Agent 协作作为 v2 演进方向。

### 风险 2：无人值守的可靠性

异步执行意味着执行期间没有人可以纠偏、Agent 幻觉没人打断、工具失败需要自动决策。

**应对**：都察院需要实时护栏（guardrails）——token 超限自动熔断、输出偏离暂停标记、调用异常降级处理。

### 风险 3：隐喻反噬

古代朝廷有些制度是为权力博弈设计的，多 Agent 系统不存在这个需求。为了"凑齐"朝廷结构而硬造角色会导致系统臃肿。

**应对**：技术需求驱动角色设计，隐喻只做命名和叙事层，不做架构约束。

### 风险 4：MVP 贪大

一上来就做齐六部 + 内阁 + 都察院 + 通政司 + 文渊阁，大概率做不完。

**应对**：先 3 个核心角色跑通闭环，再逐步"增设衙门"。

## 八、实施路线

### Phase 0：最小闭环（1-2 周）

只做 3 个角色，证明"下旨 → 办差 → 递折"能跑通：

```
御案台（任务输入）→ 内阁（任务拆解）→ 兵部执行司（单 Agent 执行）→ 结果输出
```

技术栈：Python + OpenAI API + CronJob/简单定时器 + 文件存储

### Phase 1：加入治理（2-4 周）

增加都察院（审计）和通政司（通知）：

- 每个任务执行完后自动审计
- 结果通过飞书/钉钉/邮件推送

### Phase 2：能力扩展（1-2 月）

增加文渊阁（知识库/记忆）和户部（成本管控）：

- 历史任务经验可被后续任务检索
- token 用量可追踪、可设上限

### Phase 3：多 Agent 协作（2-3 月）

引入真正的多 Agent 编排，以及 Temporal 做持久化工作流。

### MVP 最小技术栈

```
1. 任务接收接口（API / CLI / 简单 Web 表单）
2. 任务队列（Redis / PostgreSQL）
3. 单 Agent 执行器（调用 OpenAI API，带工具调用能力）
4. CronJob 定时拉取并执行任务
5. 结果存储 + 通知（邮件/飞书/钉钉）
```

## 九、总结

| 维度 | 结论 |
|------|------|
| 技术可行性 | ★★★★☆ 基础设施成熟，单 Agent 链路完全可行 |
| 业务价值 | ★★★★☆ 错峰降本 + 解放陪跑时间，价值可量化 |
| 差异化 | ★★★★☆ "朝廷治理 + 多 Agent"在市场上独特 |
| 落地难度 | ★★★☆☆ MVP 简单，无人值守可靠性是主要挑战 |
| 演进潜力 | ★★★★☆ 个人工具 → 团队平台 → 多智能体中台 |

**天枢的价值不在于"用 AI 模拟古代朝廷"，而在于"用经过历史验证的治理智慧来解决多 Agent 系统的治理难题"。这个切入角度在当前多 Agent 项目中是独特的，值得做。**

建议策略：**先 3 个角色跑通闭环，再逐步开科取士、增设衙门。**
