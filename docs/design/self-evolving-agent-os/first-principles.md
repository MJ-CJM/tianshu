# 第一性原理与设计边界

> **文档性质：目标架构与迁移建议，不是当前实现或发布承诺。**
> 当前能力以[当前实现与支持边界](../../CURRENT-STATE.md)和
> [能力事实矩阵](../../launch/capability-matrix.md)为准。

## 1. 先定义“进化”

受治理的自进化可以写成：

```text
进化 = 持久性 × 可归因性 × 独立评测 × 受权晋升 × 可回滚性
```

任何一项为零，都不能称为完整自进化：

| 变化 | 更准确的名称 | 是否属于受治理进化 |
|---|---|---:|
| 当前上下文内反思 | 在线适应 | 否 |
| 写入跨会话长期记忆 | 持久适应 | 否，除非形成候选并晋升 |
| 修改 prompt 后 reload | 重新配置 | 否 |
| 动态注册 Tool | 运行时扩展 | 否 |
| 候选 Skill/Plugin 经评测、灰度后成为 active | 产物级进化 | 是 |
| 训练并发布新模型权重 | 模型级进化 | 是，但不是 Agent OS 的必要条件 |

一个变化只有同时满足以下条件，才应进入 Evolution 账本：

1. 跨任务或进程重启持续存在；
2. 绑定不可变版本、父版本、产生者和原因；
3. 根据独立、版本化的目标与约束评测；
4. 由不同于 Candidate 的授权主体决定是否上线；
5. 能够监控、停止、恢复到 last-good，或明确声明不可逆并要求人工批准。

## 2. 自进化的核心悖论

真正的自进化系统必须保留一小部分不能由普通自进化流程修改的信任根。如果当前 Agent 可以
同时修改身份、权限、Evidence verifier、Evaluator、Promotion Authority 和回滚规则，那么
任何“进步”都无法再被可信地判断。

因此采用以下原则：

> **提案越自主，授权越独立。用户态持续进化，治理微内核不自动进化。**

微内核代码仍可以升级，但升级来自外部构建、签名和更高等级 Decision，不能由正在运行的
版本给自己签发晋升。

## 3. 八条基础公理

### 3.1 运行绑定完整快照

每个 Memorial 在第一个受管副作用前，必须绑定一个完整、不可变的 `SystemSnapshot`。
即使只变更一个插件，也产生新的完整快照摘要，未变化组件继续引用原 digest。

### 3.2 变化发生在版本之间

不要修改运行中的对象。新版本先构建、验证和预热，再让新的 continuity assignment 使用；
已开始的连续交互和长任务固定旧 generation 并排空。第一阶段的精确固定规则见
[目标领域模型](domain-and-governance.md)。

### 3.3 声明期望状态，不直接操作活体

控制面保存 desired state 与 observed state，由幂等 Reconciler 收敛。系统重启后应从持久
状态继续，而不是依赖一次性内存事件。

### 3.4 外部动作都是 Effect

LLM、工具、网络、文件、通知和支付等非确定性动作都必须经过 Effect Gateway，记录 intent、
policy decision、idempotency key、receipt 和不确定终态。

### 3.5 证据不等于授权

Evidence 证明“发生了什么、测出了什么”；Promotion Decision 决定“是否允许上线”。
Candidate 的生产者不能认证自己。

### 3.6 权限只能收窄

Manifest 描述能力上限；平台、管理员和用户策略只能进一步收窄。Candidate 无权为自己新增
secret、网络、文件或晋升权限。

### 3.7 状态迁移是发布的一部分

有状态插件必须声明 schema 版本、兼容读写范围、迁移方式和回滚能力。无法安全回退的迁移
不得自动晋升。

### 3.8 用户拥有最终收权能力

插件启用、版本固定和允许进化必须分开。用户可以使用插件但冻结它的进化，并可随时把
Canary 流量归零、固定 last-good 或触发 kill switch。

## 4. 四个时间尺度

| 循环 | 时间尺度 | 允许改变什么 |
|---|---|---|
| 执行循环 | 毫秒到分钟 | 当前 Turn/Memorial 的计划和上下文 |
| 学习循环 | 分钟到小时 | Memory 或 Candidate，不直接改变 active |
| 发布循环 | 小时到天 | Replay、Shadow、Canary、晋升、回滚 |
| 信任循环 | 人工或组织周期 | Root keys、Admission、Evaluator、预算和授权策略 |

将四个循环揉成一个“超级自进化 Agent”，会同时失去可恢复性、职责分离和因果归因。

## 5. 风险环

| Ring | 内容 | 目标自动化边界 |
|---|---|---|
| Ring 0 | 身份、审计、晋升、回滚、Root keys | 永不自动演化 |
| Ring 1 | Durable engine、PluginHost、核心协议、数据库模型 | 自动提案/评测，人工发布 |
| Ring 2 | Tool、Provider、Executor 等可执行插件 | 隔离评测和 Canary；初期人工晋升 |
| Ring 3 | Prompt、Skill、Persona、路由、普通配置 | 用户可选择受控自动晋升 |
| Ring 4 | 单次上下文、临时工作记忆 | 可在线适应，不直接固化为全局版本 |
| Ring 5 | 模型权重 | 独立离线训练和签名发布管线 |

“真正自进化”主要发生在 Ring 2–4，不要求当前 Agent 可以在线改写 Ring 0。

## 6. 非目标

本架构不追求：

- 把所有 Tianshu 模块都变成第三方插件；
- 在活跃 Python 进程中可靠卸载任意第三方模块；
- 用同一个模型完成提案、测试选择、评分和晋升；
- 把 Memory 更新、MCP tool list 变化或 reload 宣称为完整自进化；
- 第一阶段拆成多个微服务或承诺分布式部署；
- 为了“动态”而放弃静态 DAG 的预审与确定边界。
