# G2 Increment 1–2 implementation brief

Start only after G1 is committed, green, and clean. Let `N` be the last
committed migration version. Freeze v1–vN checksums; submission/outbox owns
`N+1`. Increment 2 changes no schema unless a genuinely new `N+2` is required.
Migration callbacks never control transactions themselves.

## Increment 1 — atomic submission UoW and outbox

- Add canonical JSON/hash primitives, `EdictApplicationService`,
  `SqliteUnitOfWork`, and an Outbox repository/record.
- Make Storage's application transaction the only `BEGIN IMMEDIATE` owner and
  use an `RLock`. Add connection-level insert helpers for Edict, requested
  Governance Contract, initial Memorial, and effective contract where needed.
- One transaction writes Edict, requested contract, initial Memorial,
  `edict.submitted` outbox envelope, and idempotency response snapshot.
- Idempotency authority is exact `(principal.id, key)`. Key is 1–200 chars,
  rejects controls, and is not trimmed/case-folded. Request hash excludes
  generated ids/timestamps/key, includes governance hash, and never uses
  `default=str`. Same hash returns original ids; different hash is 409 conflict.
- Dynamic migration tests cover fresh/upgrade/checksum/ledger truth. Failure at
  every insert rolls back everything; cover `:memory:` same connection,
  concurrent same-key races, principal isolation, and canonical hashes.
- Add an architecture test so governed submission writes cannot bypass the
  application service/UoW boundary.

## Increment 2 — unified ingress and recoverable outbox dispatch

- EventBus gets stable consumer names, durable/local listener separation,
  frozen durable registry, `DispatchOutcome/Report`, and dispatch that can skip
  already successful consumers. Remove Storage persistence from EventBus.
- Add `EventHistoryConsumer` (`event_history.v1`) and an Outbox Dispatcher with
  claim lease, backoff, partial-consumer progress, recovery, DLQ, lifecycle and
  readiness. Event history preserves original envelope id/time and inserts once.
- Route REST, MCP, Feishu, Telegram, submit/schedule tools, amend, CLI and Web
  through `EdictApplicationService` with stable source keys. A single UI/CLI
  submission cycle generates one key and reuses it.
- Propagate tool-call id through an invocation ContextVar; do not invent a key
  inside the tool. Request-period listeners use local registration.
- New REST submission returns 202, dedupe 200, conflict 409; remove gateway-side
  hash/pre-check authority.
- Startup order: migrations/UoW and durable consumer registration, registry
  freeze, dispatcher recovery/start, scheduler/channels, then readiness.

## Named tests and risks

- Schema/application/handoff/idempotency/write-boundary tests; outbox recovery,
  double dispatcher, expired lease, partial success, poison/backoff/DLQ,
  consumer idempotency, event history, REST/CLI/Web/Bot/MCP/Tool regressions.
- Scheduled Edicts cannot leave an unfinished initial Memorial that suppresses
  first execution. Persist a deterministic scheduling registration receipt and
  create a separate runtime Memorial at trigger time; test duplicate delivery
  and first trigger after restart.
- `ensure_chat_edict()` is a non-execution anchor and needs a dedicated
  application method or explicit boundary exception.
- Preserve all batched channel source ids in deterministic key derivation.
- Claim only durable submission plus at-least-once dispatch and CAS/unique-key
  once-effective transitions; do not call external side effects exactly-once.

## Gate

- Clean G1 handoff and migration truth first. Then focused UoW/outbox/ingress /
  dispatcher/recovery tests, relevant API/CLI/Web/channel/tool regressions,
  Web typecheck/tests, Ruff/format, mypy, import-linter, full pytest, and clean
  diff/status. Independent review after each increment.
