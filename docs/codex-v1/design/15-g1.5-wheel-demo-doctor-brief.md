# G1.5 — Self-contained wheel, offline demo, doctor, and readiness

## Objective

Make the built wheel the sole distributable unit for the backend and desktop Web
assets. A repo-external, fresh-HOME installation must start, diagnose itself,
list all built-in departments/skills, and complete one visibly marked,
deterministic, zero-network demo Edict.

## Scope and invariants

- Start after G1.4 so the black-box demo can exercise a governed staging run.
- Package six default persona departments, persona templates/sources, builtin
  skills, desktop Web assets including the existing brand image byte-for-byte,
  executor templates, license and required metadata.
- Installed package resources are immutable. Runtime/user customization lives in
  an explicit HOME/data overlay; no write may target `site-packages`.
- Remove repo-root inference from all resource consumers.
- Demo mode is explicit and never an implicit fallback for a failed live
  provider.
- Docker/container work belongs to G1.6.

## TDD sequence

### A. Wheel manifest and immutable resources

1. Build a wheel in a RED test and inspect its archive manifest.
2. Add stable `importlib.resources` locators for personas/templates/sources,
   builtin skills, Web assets, executor templates, license, and version data.
3. Test locators from repo-external cwd, read-only package directory, fresh HOME,
   cleared PYTHONPATH, and paths containing spaces/non-ASCII.
4. Assert `web/public/brand.png` (or its built output) is byte-identical to the
   current project logo; no synthetic replacement.

### B. Runtime overlay and default migration

1. Define immutable packaged defaults plus explicit writable overlay precedence.
2. Seed exactly six default persona departments only when the target persona
   table is empty, through a new versioned idempotent data migration.
3. Existing user personas/customizations must never be overwritten or duplicated.
4. Persona, COURT, skill, prompt, memory, and config writes must target the
   overlay/data root and survive package upgrades.

### C. Deterministic mock provider

1. Add RED common-dispatch tests for chat and streaming, cancellation, tool-call
   shaped responses where needed, stable usage/cost metadata, and zero network.
2. `demo` is opt-in via an explicit profile/provider; all outputs/evidence and UI
   status are visibly marked mock/demo.
3. Provider init/runtime errors for live providers remain errors and never fall
   through to demo.
4. Complete one governed mock Edict through the normal execution path.

### D. Structured doctor

1. Produce a stable versioned `DoctorReport` with table and JSON renderers.
2. Diagnose runtime mode/auth, provider, DB/schema/migration state, package
   resources, writable overlay, workspace/Git, port, liveness/readiness,
   sandbox capability, MCP, optional dependencies, and build/version identity.
3. Redact values, prefixes, headers, query strings, tokens, and paths that expose
   secrets. Every check has machine-readable id/status/evidence/remediation.
4. Doctor is read-only by default; explicit repair actions are out of scope.

### E. Liveness/readiness split

1. Liveness only proves the process/event loop can answer.
2. Readiness returns 503 for required DB/migration, scheduler/worker, resource,
   provider/profile, or mandatory sandbox failures; optional integrations are
   degraded evidence, not fatal.
3. Secure-remote readiness reveals no sensitive internals to anonymous callers.

### F. Fresh-wheel black box

1. Build once, install that exact wheel into a temporary venv with fresh HOME,
   repo-external cwd, cleared PYTHONPATH, and network-disabled demo profile.
2. Run doctor JSON, start API/Web, verify desktop assets and unchanged logo,
   list six departments and builtin skills, submit/finish a governed mock Edict,
   and cleanly stop without ResourceWarning/leaked DB/processes.
3. Record exact wheel hash/manifest and test environment. Python 3.12/Linux or
   other unavailable environments remain external evidence, not local passes.

## Required verification

- Resource/overlay/default migration/mock/doctor/health/fresh-wheel suites.
- Existing persona/skills/Web mount/provider/workspace/governance regressions.
- `uv build`, wheel archive inspection, fresh-venv black-box smoke.
- Ruff, format check, official mypy, import-linter, and clean status.
- One implementation commit, then independent spec/quality review and fixes.

## Honest limits

- Local Python/macOS evidence does not prove Linux or Python 3.12 compatibility.
- Offline demo proves packaging and workflow integration, not model quality.
- No container claim until G1.6 smoke runs with a real daemon.
